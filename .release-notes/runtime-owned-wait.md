A manager waits by ending its turn, and Runtime wakes it. The `await_event` coordination tool, `CoordinationVerbs.awaitEvent`, `DEFAULT_AWAIT_EVENT_TIMEOUT_MS`, and the `awaitTimeoutMs` option of `supervise`, `supervisorAgent` and `driverAgent` are removed, and a profile that grants `agent_runtime_coordination_await_event` is refused before any spend. While a manager has work open (a worker running, an unread result, finding or lead message, or a tool call still running past its fence), a turn that ends is a wait: Runtime blocks on the coordination bus with no model turn and starts the next turn of the same session with one input listing what happened. The new `wake` option (`heartbeatMs`, default 15 min; `debounceMs`, default 2 s while other workers still run; `deadlineWarningMs`, default 15 min and at most a quarter of the manager's time) sets when it is woken; the deadline wake asks for `submit_result` and lifts the open-work refusal. A steer or answer to a manager with no live inbox is queued as its next wake input instead of being refused `runtime-has-no-inbox`. A fenced tool call (`submit_result`, product node tools such as Knowledge) still running at its fence returns `{ running: true, receipt }`, and its outcome arrives as a `tool-outcome` event in the next wake, never as a "call again" instruction. A program joins its own workers with `context.verbs.awaitSettlement({ workerIds })` (`api.await_settlement` in code mode), which takes nothing from the manager's inbox. `observe_agent` reports a child manager's own harness activity, and a manager waiting between turns says so. A Claude Code manager runs with `ENABLE_PROMPT_CACHING_1H=1`, so a wake within the hour reads its context back from cache. The driver loop record adds `wakes` and `waitedMs`. Sandbox `tool-heartbeat` and `tool-slow` frames are no longer recorded as tool calls. Measured 2026-10-05 on two Discovery roots, 18 of 88 model turns did nothing but wait, each re-reading about 140K cached tokens.
